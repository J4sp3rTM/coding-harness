# Agent Note: JSONL 恢复后缀取代

状态：已实现

[English](2026-08-25-jsonl-recovery-suffix-supersession.md) | 中文

## 问题

JSONL 后端只在单个进程内协调一个 writer。若另一个进程在原 writer 仍存活时加载开放轮次，loader 可能先持久化确定性的中断轮次 closer 和构造函数 seed 边界，随后原 writer 才 flush 下一批。原批次会从第一个合成 closer 的序号开始。即使其中一个分支只包含恢复记录，工件仍会在同一序号下包含两个分支。

## 决策

扫描器只识别一种狭窄的取代模式。冲突行必须精确从当前事件后缀的起点开始，且整个后缀只能包含合成中断工具结果、一个可选且轮次匹配的 `step/end`、一个原因为 `interrupted` 的 `turn/end`，以及一个可选的尾部 `session/end-seed`。扫描器移除该逻辑后缀，并接纳原 writer 的连续续写。该规则先于打包行重叠处理运行，因此打包续写会保留分支点后的每个事件。

冲突行的首个序号在索引事件前缀前会先校验为非负安全整数，因此格式错误的序号会报告损坏，而不是抛出 `RangeError`。其他冲突普通事件、不匹配的恢复记录、seed 边界后的事件和向前序号缺口仍属于损坏。物理仅追加工件不会被改写；每次扫描都会派生相同的连续逻辑历史。

## 后果

当原 writer 的延迟 flush 只取代确定性恢复输出时，会话仍可加载。该规则不会让并发 writer 成为受支持行为：两个进程仍可能产生无法协调的分支，每会话一个活动 writer 的部署要求保持不变。运维人员会保留完整物理工件用于诊断，而模型与 UI 会收到一份连续事件历史。

## 测试

扫描器规格覆盖两种合成工具结果 code、有无开放步骤或 seed 边界的恢复、重叠的打包续写、对不匹配或无关已提交事件的拒绝，以及进入取代判定的负数或非整数序号。触发该规则的捕获会话工件会扫描为连续的 `0..346659` 逻辑历史。

## 考虑过的替代方案

将每个向后序号都视为重复被否决，因为不同的已提交事件会被静默丢弃。在第一次冲突处截断被否决，因为有效的后续轮次会丢失。改写压缩仅追加存储的中部被否决，因为逻辑取代是确定性的，并且会保留原始证据。
